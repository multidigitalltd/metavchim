# 04 · אבטחה ופרטיות

המערכת מחזיקה את הנכס היקר ביותר של סוכנות: מאגר הקונים והמוכרים שלה. דליפה בין סוכנויות = מוות מסחרי של המוצר. לכן אבטחה כאן היא לא סעיף — היא תנאי קיום.

## 1. מודל איומים (תמצית)

| איום | וקטור | הגנה עיקרית |
|------|-------|-------------|
| דליפת דאטה בין סוכנויות | באג בקוד / IDOR | בידוד תלת-שכבתי: Scope + Policy + **RLS בבסיס הנתונים** |
| גניבת מאגר ע"י עובד עוזב | ייצוא המוני | הרשאות ייצוא נפרדות, Rate Limit על שליפות, התראת אנומליה, Audit |
| השתלטות על חשבון | Phishing / סיסמה חלשה | 2FA (חובה למנהלים), נעילת Brute Force, התראת התחברות חדשה |
| Webhook מזויף (WhatsApp/Kanko/טלפוניה) | קריאה חיצונית | אימות חתימה לכל Webhook + Replay Protection (timestamp + nonce) |
| הזרקת פרומפט דרך שיחה/הודעה | לקוח אומר לסוכן הקולי "תן לי את כל הקונים" | ה-LLM מקבל רק נתונים שהוא מורשה להם; פעולות דרך Tool-Calls מוגדרים בלבד; אין גישת SQL/API חופשית ל-LLM |
| ספאם/שימוש לרעה בוואטסאפ | שליחה המונית | אישור מתווך לפני שליחה, מכסות, Opt-out מנוהל, ניטור Quality Rating |
| SSRF/RCE דרך העלאות | קובץ זדוני | ולידציית MIME אמיתית, אחסון מחוץ ל-Web Root (S3), ללא הרצה, סריקת AV |

## 2. בידוד דיירים (Tenant Isolation) — תלת-שכבתי

1. **שכבת אפליקציה**: `TenantContext` נקבע פעם אחת ב-Middleware מתוך ה-Session/Token; Global Scope מוסיף `tenant_id` לכל שאילתה אוטומטית. אין העברת `tenant_id` מהלקוח — לעולם.
2. **שכבת הרשאה**: Policy לכל ישות בכל Endpoint — גם בתוך הדייר (סוכן רואה רק את הלידים שלו אלא אם הוא מנהל).
3. **שכבת DB**: PostgreSQL Row-Level Security — החיבור מריץ `SET app.tenant_id`; פוליסת RLS חוסמת כל שורה זרה. **גם קוד שגוי לא מדלף.**

בדיקות אוטומטיות: סוויטת בדיקות "Cross-Tenant" שמנסה לגשת לכל Endpoint עם משתמש מדייר אחר — חובה ירוקה בכל CI.

## 3. זהות והרשאות

- **אימות**: סיסמאות (Argon2id) + 2FA TOTP (חובה לתפקידי Admin/Owner); כניסת Magic-Link כאופציה למתווכים; Session קצר + Refresh; ניתוק מרחוק של מכשירים.
- **RBAC מבוסס Capabilities** (לא בדיקות Role גולמיות):
  - `properties.view|create|edit|delete`, `buyers.view_all|view_own`, `offers.send`, `collaboration.share`, `billing.manage`, `data.export`, `settings.manage`...
  - תפקידים מובנים: Owner, Admin, Agent, Assistant (ללא ייצוא/מחיקה), Viewer.
  - Agency יכולה להתאים תפקידים; Capabilities הן היחידה הנבדקת בקוד.
- **API Keys** (Enterprise): Scoped, ניתנות לביטול, עם Rate Limit נפרד, לעולם לא בטקסט גלוי אחרי יצירה.

### 3.1 שני כללים שנאכפים אוטומטית

שני הכללים האלה נשברו בפועל, ולכן לכל אחד מהם יש היום בדיקה שמפילה את ה-CI ולא רק סעיף במסמך.

**א. כל נתיב מצהיר מי רשאי להגיע אליו.** ה-`AuthGuard` הגלובלי דורש Session מכל נתיב שאינו `@Public`, ולכן נתיב ששכחו ממנו `@RequireCapability` *עובד* — הוא פשוט פתוח לכל מי שמחובר למשרד, ואי אפשר להבחין בין "פתוח בכוונה" ל"נשכח". לכן כל Handler חייב אחת מארבע ההצהרות:

| הצהרה | משמעות |
|--------|---------|
| `@RequireCapability(...)` | נדרשת יכולת מסוימת |
| `@AnyAuthenticated()` | פתוח לכל מחובר — החלטה מודעת, לנתיבים שכל תוכנם נגזר מהמשתמש עצמו |
| `@Public()` | ללא Session כלל (login, health, דפי הצעה ונחיתה) |
| `@PlatformAdmin()` | ניהול הפלטפורמה, מעל כל הדיירים |

`apps/api/src/common/auth-coverage.test.ts` קורא את הבקרים ב-AST ונופל על נתיב בלי הצהרה.

**ב. `ownershipFilter` חל גם על כתיבה, לא רק על קריאה.** הכשל שחזר על עצמו בשבעה מקומות היה זהה: `list`/`getById` סוננו לפי בעלות, אבל הפעולה על אותה ישות נשלפה לפי `{ id, tenantId }` בלבד. התוצאה — סוכן שאינו יכול *לראות* ליד של עמית כן יכול לשנות את הסטטוס שלו, לכתוב בו הערה, ולשלוף את מספר הטלפון של הקונה. לפעולה על ישות בודדת יש שערים ב-`common/ownership.ts`: `assertLeadAccess` / `assertBuyerAccess` / `assertMatchAccess`, וכולם מחזירים 404 ולא 403 — תשובה שונה לישות קיימת-אך-לא-שלי מסגירה את קיומה.

## 4. הגנת נתונים

- **תעבורה**: TLS 1.2+ בלבד, HSTS.
- **במנוחה**: הצפנת דיסק מלאה + **הצפנה ברמת עמודה ל-PII** (טלפון, אימייל, שם לקוח קצה, פרטי בעלים) עם מפתחות מנוהלים (KMS/סודות מנוהלים); `phone_hash` (HMAC) לחיפוש ללא פענוח.
- **הקלטות שיחה**: S3 פרטי, גישה רק דרך URL חתום קצר-תוקף, לאחר בדיקת הרשאה.
- **סודות**: Environment/Secret Manager בלבד. אין סודות בקוד, בלוגים או בתשובות API. סריקת סודות ב-CI.
- **לוגים**: ללא PII בלוגים טכניים (מיסוך אוטומטי); Stack Traces לעולם לא מוצגים למשתמש.

## 5. אבטחת קלט/פלט (כללי המחייבים כל PR)

- כל קלט: ולידציה בצד שרת עם סכמות Zod (דרך NestJS Pipes) — טיפוס, אורך, טווח, פורמט. הלקוח הוא נוחות, לא אבטחה.
- כל פלט: Escaping לפי הקשר (React עושה זאת כברירת מחדל — אסור `dangerouslySetInnerHTML` על תוכן משתמש).
- SQL: אך ורק Prisma/Parameterized Queries. `$queryRawUnsafe` וקונקטנציית SQL = חסימת PR.
- CSRF: SameSite Cookies + טוקן על פעולות משנות-מצב; CORS מוגדר במפורש (Origin ידועים בלבד).
- העלאות: הרחבה + MIME אמיתי (magic bytes) + גודל + הרשאה; שמות קבצים מוחלפים (ULID); העלאה ישירה ל-S3 עם Presigned URL — קבצים לא נוגעים בשרת האפליקציה.
- Redirects: רשימת יעדים מותרת בלבד.
- Mass Assignment: DTO מפורש לכל Endpoint (Zod `strict()`) — שדות לא מוצהרים נדחים.
- Prototype Pollution / ReDoS: תלות ב-Lint rules ייעודיים + סריקת תלויות.

## 6. אבטחת אינטגרציות

- **Webhooks נכנסים** (WhatsApp, טלפוניה, Kanko): אימות חתימה (HMAC-SHA256 עם סוד ייעודי פר-אינטגרציה) + בדיקת Timestamp (חלון 5 דקות) + Idempotency Key נגד Replay. כשל אימות → 401 + התראה.
- **Webhooks יוצאים**: חתימה שאנחנו מספקים + Retry עם Backoff + השהיה אוטומטית של יעד כושל.
- **Rate Limiting**: לכל Endpoint ציבורי (per-IP + per-token); הקשחה נוספת על login, שליחת הודעות וייצוא.
- **הסוכן הקולי וה-LLM**: עקרון "יכולות סגורות" — ה-LLM פועל דרך רשימת Tools מוגדרת (שליפת נכס ספציפי שהשיחה עוסקת בו, קביעת תור, יצירת סיכום). אין לו יכולת שליפה חופשית, אין גישה לנתוני דיירים אחרים, וכל Tool עובר את אותן בדיקות הרשאה כמו משתמש. תוכן שיחה = קלט לא אמין תמיד.

## 7. פרטיות בשיתופי פעולה (הפיצ'ר הרגיש ביותר)

- **אנונימיזציה אמיתית, לא הסתרה**: ביקוש משותף הוא רשומה נפרדת ללא PII — תקציב מעוגל לטווח, אזור ברמת עיר/שכונה, ללא שם/טלפון. הקישור לקונה המקורי מוצפן במפתח של סוכנות המקור בלבד.
- **חשיפה מדורגת**: גם הנכס המוצע נחשף בהדרגה (אזור+מאפיינים → כתובת מלאה רק אחרי אישור חיבור).
- **הסכמה כפולה**: חיבור נפתח רק כששתי הסוכנויות אישרו, והקונה הביע עניין.
- **שליטה מלאה לסוכנות**: אילו קונים משותפים, לאילו אזורים, ממי מקבלים הצעות, ביטול שיתוף בכל רגע (מסיר ביקושים פעילים).
- **Audit מלא**: כל צפייה בביקוש, כל הצעה, כל חשיפת פרט — נרשמים. "מי ראה מה ומתי" זמין לסוכנות.
- **K-Anonymity בסיסי**: אם שילוב אזור+תקציב+דרישות ייחודי מדי (עלול לזהות אדם), הביקוש מוצג ברמת הכללה גבוהה יותר.

## 8. תאימות רגולטורית

- **חוק הגנת הפרטיות (כולל תיקון 13, בתוקף מאוגוסט 2025)**: המערכת = "מחזיק מאגר" עבור הסוכנויות. נדרש: רישום פעילויות עיבוד, מנגנון זכות עיון/תיקון/מחיקה ללקוח קצה, נוהל אירוע אבטחה (זיהוי → הכלה → דיווח לרשות תוך הזמן הקבוע), הסכם עיבוד נתונים (DPA) מול כל סוכנות.
- **הקלטת שיחות**: הודעה בתחילת שיחה שהשיחה מוקלטת ("שיחתך תוקלט לצורך שיפור השירות") — מובנה בתסריט הסוכן הקולי.
- **דיוור/וואטסאפ**: שליחה רק ללקוח שיצר קשר או נתן הסכמה; Opt-out מכובד מיידית וגורף בכל הערוצים; רישום הסכמות עם מקור וזמן.
- **זכות למחיקה**: מחיקת לקוח קצה מנקה PII מכל הישויות (כולל תמלולים) תוך שמירת רשומות אנונימיות לסטטיסטיקה.

## 9. תהליך אבטחה שוטף

- סריקת תלויות (Dependabot/`pnpm audit`) — שבועי + חסימת CVE קריטי ב-CI.
- SAST (TypeScript strict + ESLint security rules + Semgrep) בכל PR.
- בדיקת חדירות חיצונית לפני עליית Production ואחת לשנה.
- תוכנית תגובה לאירוע: Runbook כתוב, איש קשר, תרגול חצי-שנתי.
- עיקרון הרשאה מינימלית גם פנימית: גישת Production לצוות מצומצם, דרך Bastion, עם Audit.
