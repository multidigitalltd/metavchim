## 2. עקרונות

1. **מהיר בזכות פשטות**: הפתרון הקל ביותר במשאבים קודם. אין רכיב תשתות חדש בלי צורך מוכח (למשל: pgvector לפני Elasticsearch; Redis לפני Kafka).
2. **שום דבר כבד ב-Request**: תמלול, חילוץ, התאמות, שליחות, סנכרונים — הכל בתורים. ה-Request רק רושם ומחזיר; ההתקדמות מדווחת ב-WebSocket.
3. **מדידה לפני אופטימיזציה**: APM מהיום הראשון (שאילתות איטיות, N+1, זמני תור). תקציבי ביצועים ב-CI (Lighthouse CI על מסכי מפתח).

## 3. שכבות Cache

| שכבה | תוכן | TTL / פינוי |
|------|------|-------------|
| CDN (Cloudflare) | נכסים סטטיים, תמונות, דפי הצעה (חלק סטטי) | לפי גרסה (hash בשם קובץ) |
| Redis — אפליקציה | מוני דשבורד, יתרת קרדיטים, הגדרות דייר, Feature Flags | 1–5 דק' + פינוי באירוע שינוי |
| Redis — Read Models | רשימות התאמות מחושבות, ספירות "קונים מתאימים" | פינוי ב-`MatchesComputed` |
| HTTP | ETag/Last-Modified על משאבי API יציבים | |

- כללי מפתח: Cache מפונה **באירוע**, לא רק ב-TTL; אין Cache על נתונים חוצי-דיירים; מפתחות Cache כוללים `tenant_id` תמיד.

## 4. בסיס נתונים

- שאילתות דרך אינדקסים בלבד למסלולים חמים (מסמך 03); `EXPLAIN ANALYZE` לכל שאילתה חדשה במסלול חם.
- Eager Loading מוצהר — בדיקת N+1 אוטומטית בסביבת פיתוח (חריגה = כישלון בדיקה).
- Pagination בכל רשימה (Cursor-based ברשימות גדולות); ללא `COUNT(*)` יקרים — מונים מ-Read Models.
- Connection Pooling (PgBouncer) לפני הוספת Replicas.
- צמיחה: Read Replica לדוחות → פרטישן לטבלאות אירועים (`messages`, `audit_log`, `usage_events` לפי חודש) → אין צורך צפוי מעבר לזה בסקייל של אלפי סוכנויות.

## 5. מנוע ההתאמות בפרופיל ביצועים

- **שלב 1 — סינון גס ב-SQL** (מילישניות): עיר ∩ תקציב ∩ חדרים ∩ סוג → מאות מועמדים לכל היותר.
- **שלב 2 — ניקוד מפורט בקוד**: משקלות לכל קריטריון (מיקום, מחיר, must/nice, קומה, מעלית...) → `score_breakdown`.
- **שלב 3 — העשרה סמנטית (אופציונלי, שלב מתקדם)**: דמיון וקטורי על טקסט חופשי (pgvector) כמרכיב ניקוד נוסף, לא כמסנן.
- חישוב תמידי-מראש (באירועי שינוי) — המסך רק קורא תוצאות; אף פעם לא מחשבים ב-Request.
- Debounce: שינויים מרובים ברצף על אותה ישות = חישוב אחד (Job ייחודי לפי ישות).

### 5.1 סבב הרענון — מה שאינו נובע מרשומה בודדת

חישוב באירועי שינוי מכסה כמעט הכול: שמירת נכס סורקת אותו מול כל
הקונים, ושמירת קונה מול כל הנכסים. שלושה מצבים נופלים בין הכיסאות,
ולכולם `MatchRefreshService` (API, לא Workers — הוא מריץ את מנוע
ההתאמות עצמו, ועותק שני שלו היה מתפצל):

| מה השתנה | מה מפעיל את הסבב |
|---|---|
| משקלי ההתאמה של המשרד | `PATCH /settings/match-weights` — סבב ברקע, מיד |
| גרסת מנוע ההתאמות (`MATCH_ENGINE_VERSION`) | הסורק, בהשוואה למה שנשמר במשרד |
| הזמן עבר (התאמת מועד הכניסה נמדדת מול `now`) | הסורק, אחת ליממה |
| כלום — בקשה מפורשת | `POST /matches/refresh` (`settings.manage`) |

- הכלל עצמו טהור ובדוק: `matchRefreshDue` ב-`packages/shared`.
- הסבב עובר על **הנכסים בלבד** — כל נכס נסרק מול כל הקונים, ולכן
  מעבר על הקונים היה מחשב שוב את אותם צמדים.
- **התראה אחת לסבב** ולא אחת לנכס: `recomputeForProperty` נקרא עם
  `silent`, והסיכום נשלח לבעלים פעם אחת. אחרת לילה אחד היה מייצר
  עשרות התראות "נמצאו קונים חדשים".
- תקרת נכסים לסבב; חריגה נרשמת כ-`ok: false` והסבב הבא רץ מיד.
- הסבב גם מנקה התאמות `suggested` של נכסים שיצאו מהשיווק או נמחקו —
  המסלול היחיד שנוגע בהן, כי נכס כזה אינו נסרק בשום מקום אחר.

## 6. תורים ועיבוד רקע

- תורים נפרדים לפי אופי: `realtime` (וואטסאפ נכנס, סיכומי שיחה), `ai` (תמלול/חילוץ — מוגבל מקבילות לפי מכסות ספק), `matching`, `notifications`, `sync` (יומן, Kanko), `low` (ניקויים).
- כל Job: Idempotent, Retry עם Backoff, Dead Letter Queue עם התראה.
- עבודות ארוכות = Batches (למשל שליחת הצעות ל-100 קונים = 100 Jobs קטנים, לא אחד ענק).
- Rate Limiting פנימי מול ספקים (WhatsApp/LLM) בתוך ה-Adapter — לא בקוד העסקי.

## 7. Frontend

- Code Splitting לפי מסך; אין טעינת JS/CSS שלא נדרש למסך הנוכחי.
- תמונות: WebP/AVIF, גדלים רספונסיביים, Lazy Load; תמונות נכסים עוברות עיבוד (Resize+דחיסה) בהעלאה.
- מטמון PWA לנכסים סטטיים + מסכי ליבה; מצב קריאה בסיסי גם ברשת חלשה (שטח!).
- ללא ספריות כבדות כשווניל/רכיב קל מספיק; תקציב Bundle למסך ראשי: < 200KB gzip.
- **טבלאות גדולות (נכסים/קונים/התאמות)**: העמוד לא טוען הכל — Pagination בצד שרת (50–100 שורות לעמוד, Cursor-based) + חיפוש/סינון ב-DB דרך אינדקסים; ברשימות גלילה ארוכות — וירטואליזציה (TanStack Virtual: מרונדרות רק ~20 השורות שנראות במסך). כך גם טבלה של 100,000 רשומות מרגישה מיידית — הביצועים נקבעים ע"י תכנון השאילתה והרינדור, לא ע"י "כובד המנוע".

## 8. סקיילינג אופקי

- האפליקציה Stateless (Sessions ב-Redis) → הוספת שרתי App/Workers = ליניארית.
- Voice Agent הוא הרכיב הרגיש להשהיה — מבודד ל-Deploy נפרד כשנפח השיחות עולה (הגבול המודולרי כבר קיים).
- יעד תכנון: 1,000 סוכנויות פעילות, 50K שיחות/חודש, 1M הודעות/חודש — על תשתית צנועה (2–3 App nodes + 2 Workers + PG יחיד עם Replica). מעבר לזה — הפרדת שירותים לפי המודולים הקיימים.
