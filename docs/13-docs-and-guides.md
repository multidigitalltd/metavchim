# 13 · תיעוד והדרכות — איפה כל דבר יושב ואיך כותבים

> מסמך שאיש לא מוצא שווה למסמך שלא נכתב. המסמך הזה אומר איפה כל תוכן חי,
> מי קורא אותו, ואיך מוסיפים תוכן שלא יתיישן ביום שמישהו מתקן עותק אחר שלו.

## 1. שלושה קהלים, שני מקורות

| קהל | מה הוא צריך | איפה זה חי | פורמט |
|-----|-------------|------------|-------|
| **מתווך/ת מחובר/ת** | "איך עושים X" מתוך המערכת, עם צילומי מסך | „הדרכות” בתפריט מפנה ל-`/docs`; עמוד לכל נושא ב-`/docs/<topic>` | עמוד לכל נושא, חיפוש, מדריכים קשורים |
| **מי שעדיין לא בפנים** — משרד ששוקל, בונה אתרים, מודל שפה, מי שמקים חיבור | אותו תוכן בלי התחברות, עם עוגנים | `/docs`, `/docs/<נושא>`, `/docs/api`, `/docs/telephony` | HTML ציבורי ומאונדקס |
| **כלי בינה מלאכותית** | טקסט נקי להדבקה | `/docs/md` (הכול) · `/docs/md/<topic>` (נושא) | Markdown, `text/markdown; charset=utf-8` |
| **הצוות** | ארכיטקטורה, אבטחה, תפעול, החלטות | `docs/*.md`, `docs/adr/` | Markdown במאגר |

**שני המקורות:**

1. `apps/web/src/lib/guide-content.ts` — **כל** התוכן למשתמשים: המדריכים (`GUIDES`),
   האזורים (`GUIDE_AREAS`), סעיפי המסגרת ומילון המונחים (`DOC_TOPICS`), ופונקציות
   ה-Markdown. שלושת המסכים והנתיבים נגזרים ממנו. אין טקסט הדרכה ב-JSX.
2. `docs/` — תיעוד הצוות. ממוספר לפי נושא, ADR לכל החלטה.

הכלל שמאחורי החלוקה: **מה שמשתמש צריך לדעת נכתב פעם אחת ב-`guide-content.ts`;
מה שמפתח צריך לדעת נכתב פעם אחת ב-`docs/`.** שני עותקים של אותו הסבר נפרדים
ביום הראשון שמישהו מתקן אחד מהם — זה כבר קרה כאן עם תוויות המקורות ועם מונחי
ההפניות, ובשני המקרים משתמש ראה שני דברים סותרים.

## 2. מבנה מדריך

```ts
{
  id: "whatsapp",          // הכתובת: /docs/whatsapp, /docs/md/whatsapp
  area: "daily",           // start · daily · network · office · account
  title: "…",              // כותרת — שם המסך + מה מקבלים ממנו
  summary: "…",            // שורה אחת לכרטיס באינדקס. לא הפסקה הראשונה של המדריך.
  intro: "…",              // משפט-שניים: מה זה, ולמה זה טוב לי
  image: "/guides/x.png",  // צילום מסך ב-public/guides — השער בודק שהוא קיים
  steps: [{ title, body }],          // "איך עושים" — הסדר הוא סדר הפעולה
  sections: [{ title, body, bullets?, note?, image? }], // "למה זה ככה", "מה קורה כש…"
  faq: [{ q, a }],                   // שאלות שנשאלו בפועל, לא שנוח לענות עליהן
  related: ["leads", "calls"],       // מזהים בלבד — מזהה שגוי מפיל את verify:assets
  tip: "…",                          // משפט אחד, אופציונלי
}
```

**הסדר בעמוד קבוע**: צעדים → העמקה → שאלות נפוצות → טיפ → קשורים. הצעדים ראשונים
כי "איך עושים" היא השאלה שאיתה נכנסים; ההעמקה אחריהם כי "למה" מגיע רק אחרי שניסו.

**האזור הוא לפי מתי צריך את זה**, לא לפי איזה מסך זה: ייבוא נתונים הוא "להתחיל"
גם אם הוא יושב בהגדרות; אוטומציות הן "ניהול המשרד" גם אם הן פותחות משימות יומיות.

## 3. סגנון — יפה, מקצועי, קליט

- **עברית פשוטה, גוף שני רבים** ("אתם", "לוחצים"), בלי סלנג ובלי ז'רגון תוכנה.
  מונח טכני שחייב להופיע (Webhook, DNS) מוסבר במילון המונחים ומקושר משם.
- **פותחים בתועלת, לא במסך.** "כל שיחה נרשמת, מתומללת ומסוכמת — בלי שאיש יקליד"
  ולא "מסך השיחות מציג את רשימת השיחות".
- **צעד = פעולה אחת + תוצאה.** כותרת בפועל ("מוסיפים למסך הבית"), גוף שאומר
  איפה לוחצים ומה קורה אחר כך.
- **מה המערכת עושה לבד — כותבים במפורש.** "ההקלטה נמחקת אחרי התמלול",
  "שום הודעה לא יוצאת בלי אישורכם". שקיפות היא מה שבונה אמון במוצר עם AI.
- **כל "לא" מקבל "למה".** "אי אפשר לכבות את מועדי הבלעדיות — הם נובעים מהחוק."
- **מספרים מדויקים** כשהם קיימים בקוד (15 דקות, 250 שורות, 85%), ולא "כמה דקות".
- **אין הבטחות על מה שלא קיים.** תכונה בתכנון נכתבת ב-`docs/09`, לא במדריך.
- **שפת ההפניות**: התמורה משולמת על *ההפניה* ולא על *הלקוח*. ניסוחים של
  "קניית/מכירת לידים" נחסמים ב-`verify:language` (ראו `REFERRAL_TERMS`).
- **מרכאות עבריות** „כך” לשמות של כפתורים ומסכים; גרשיים ‎"‎ רק בתוך מחרוזות
  שבהן זה כבר מקובל.

## 4. צילומי מסך

- יושבים ב-`apps/web/public/guides/<id>.png`, מוצגים בראש המדריך ובסעיפים.
- מצב בהיר, נתוני דמו (לעולם לא לקוח אמיתי), רוחב 1280–1440, החלק העליון של המסך
  (התמונה נחתכת ל-460px גובה עם `object-position: top`).
- קובץ חסר עובר קומפילציה ומגיע למשתמש כתמונה שבורה — לכן `verify:assets`
  בודק כל נתיב שכתוב בקוד.

## 5. השערים שרצים על התוכן

| שער | מה הוא תופס |
|-----|-------------|
| `verify:assets` | תמונה חסרה · `href` פנימי ל-404 · `related` למזהה שאינו קיים · אזור שאינו ברשימה · מזהה כפול · סעיף מסגרת שלא נכנס ל-`docsMarkdown()` |
| `verify:language` | ניסוח מסחרי במסכי ההפניות ובהדרכות |
| `verify:typography` | טקסט מתחת ל-14px או משקל דק בעמודי ההדרכה והתיעוד |
| `typecheck` | שדות חובה חסרים במדריך, טיפוס שגוי ב-passage |

הרצה מקומית: `pnpm --filter @metavchim/web verify:assets verify:language verify:typography`.

## 6. תיעוד הצוות (`docs/`)

- **מסמך ממוספר לנושא**, ADR להחלטה. לא פותחים מסמך חדש לתכונה — מוסיפים סעיף
  במסמך הנושא (אינטגרציה חדשה → 05, שער CI חדש → 08 או 06).
- **מצב בפועל מסומן**: ✅ / 🟡 / ⬜. סעיף תכנון שטרם נבנה אומר "יעד ולא מצב".
- **הערות בקוד מסבירות למה, לא מה.** ההיסטוריה של החלטה — כולל התקלה שהובילה
  אליה — נכתבת ליד הקוד, כי שם היא נקראת לפני שמישהו "מפשט" אותה.
- **ההצהרות המשפטיות** (`/accessibility`, `/privacy`, `/terms`) מתארות רק מה
  שקיים. שינוי בתכונה שהן מזכירות מחייב עדכון שלהן באותו PR.
