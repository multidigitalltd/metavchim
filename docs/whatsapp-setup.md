# חיבור וואטסאפ עסקי — מצב המימוש, הערכים וההחלטות הפתוחות

> **הצעדים עצמם — שלב אחרי שלב, מהתיק העסקי ב-Meta ועד ההודעה הראשונה
> שנכנסת כליד — יושבים בתיעוד הציבורי: [`/docs/whatsapp`](../apps/web/src/app/docs/whatsapp/page.tsx).**
> הם שם ולא כאן כי מי שמבצע אותם לא בהכרח מחובר למערכת, והוא שולח את
> הקישור למי שעוזר לו. המסמך הזה מחזיק את מה שאינו צעד: מה בנוי, איפה
> כל ערך נשמר, ומה טרם הוכרע.

## 1. מה בנוי היום

| זרם | מצב | איך |
|-----|-----|-----|
| הודעה נכנסת למספר העסקי של משרד → ליד / כרטיס קיים | ✅ | Webhook מאומת (App Secret), ניתוב לפי `whatsappNumber` של המשרד, מניעת כפילויות לפי `message_id` |
| הסוכן האישי — שיחה בוואטסאפ עם משתמש מקושר | ✅ | קו הסוכן = `whatsappPhoneNumberId` של הפלטפורמה; קישור מכשיר בקוד חד-פעמי מהפרופיל |
| מענה למספר לא רשום שכותב לסוכן | ✅ | `whatsappProspectReply`, לכל היותר פעם בשבוע למספר |
| התראות לסוכן (שיחה שלא נענתה, תשובת לקוח במייל) | ✅ | תבנית מאושרת מחוץ לחלון 24h; בתוך החלון — טקסט חופשי |
| טופס „מה אתם מחפשים” ללקוח אחרי שיחה שלא נענתה | ✅ | תבנית `whatsappIntakeTemplate`; בלעדיה — משימה לסוכן עם ההודעה מוכנה |
| תזכורת לפני סיור ללקוח ולמי שגר בנכס | ✅ | תבנית `whatsappViewingReminderTemplate`; בלעדיה — מייל בלבד |
| הצעות נכסים ללקוחות | ✅ בכוונה לא מהשרת | נפתחות מוכנות בוואטסאפ של הסוכן (`wa.me`); הוא קורא ולוחץ שלח — הרגע האחרון לפני שהלקוח מקבל טקסט בשם המשרד |
| קליטת נכס בהודעה קולית בוואטסאפ | ⬜ | הקולט מפרש `text` בלבד; קליטה בקול קיימת באפליקציה |
| חיבור מספר בידי כל משרד (Embedded Signup) | ⬜ | ראו §4 |

הפירוט הטכני של התבניות, הפרמטרים וההתנהגות כשהן ריקות: [05 · אינטגרציות §1](05-integrations.md).

## 2. הערכים ואיפה הם נשמרים

| ערך | מאיפה ב-Meta | איפה אצלנו |
|-----|--------------|------------|
| App Secret | App settings ← Basic | `/platform` ← „וואטסאפ (Meta Cloud API)” |
| Verify Token | ממציאים | `/platform` **וגם** ב-Meta (Webhook), אותה מחרוזת |
| Access Token (System User, ללא תפוגה) | Business Settings ← System users | `/platform`; חלופה: `WHATSAPP_ACCESS_TOKEN` בסביבה |
| Phone Number ID | WhatsApp ← API Setup | `/platform`; חלופה: `WHATSAPP_PHONE_NUMBER_ID` בסביבה |
| WhatsApp Business Account ID | WhatsApp ← API Setup | נשמר בצד — נדרש ל-Embedded Signup |
| ארבע התבניות + שפה, מענה למספר לא רשום | Message Templates (אחרי אישור) | `/platform`, אותו כרטיס |
| המספר העסקי של כל משרד | Add phone number ב-WABA | ניהול משרד ← „וואטסאפ” (`whatsappNumber`), ספרות בלבד |

**„בדוק חיבור”** בכרטיס הפלטפורמה פונה ל-Meta על המספר ומדווח אם הוא עונה —
זו הבדיקה שמפרידה בין „הטוקן נשמר” ל„הטוקן עובד”.

`platform-settings-coverage.test.ts` מפיל את ה-CI על כל מפתח שנקרא בקוד ואין
דרך לכתוב אותו מהמסך — הלקח מ-`whatsappIntakeTemplate`, שנקרא ומעולם לא
היה בסכימת הכתיבה.

## 3. מצב האפליקציה ב-Meta

במצב **Development** הודעות נכנסות עובדות במלואן, אבל שליחה אפשרית רק
למספרים שברשימת הבדיקה. מעבר ל-**Live** דורש: אימות עסק שהושלם, App Review
על `whatsapp_business_messaging` ו-`whatsapp_business_management`, והעברת
האפליקציה למצב Live. עד אז — הסוכן האישי, ההתראות והתזכורות מגיעים רק
למספרים שברשימה.

## 4. החלטות פתוחות

### ישירות מול Meta, או דרך BSP?

| | ישירות | BSP (360dialog, Twilio…) |
|---|---|---|
| זמן להקמה | שבועות (App Review) | יומיים |
| עלות | מחיר Meta בלבד | + תוספת לכל הודעה |
| תלות | אין | בספק |
| מתאים ל | טווח ארוך | לצאת לאוויר מהר |

האדפטר (`MessagingProvider`, [ADR-004](adr/ADR-004-whatsapp.md)) זהה בשני
המקרים; הערכים והנתיבים שונים. המימוש הנוכחי הוא ישירות מול Meta.

### חיבור מספר בידי כל משרד (Embedded Signup)

מסלול נפרד ב-Meta שדורש רישום כ-**Tech Provider**:

1. בעל המשרד לוחץ „חבר וואטסאפ” אצלנו ← נפתח פופאפ של Meta.
2. מתחבר עם הפייסבוק שלו, בוחר או יוצר WABA, מוסיף את המספר שלו.
3. חוזר אלינו `code` ← ממירים אותו בשרת ל-*customer-scoped business token*.
4. רושמים את האפליקציה שלנו ל-webhooks של ה-WABA שלו.
5. נשמרים לו: WABA ID, phone number ID, token.

מה שחשוב לדעת מראש:

- **כל משרד משלם ל-Meta בעצמו** — חייב אמצעי תשלום ב-WABA שלו. רק Solution
  Partner (מסלול כבד יותר) יכול לחלוק קו אשראי אחד. זה משפיע ישירות על
  מודל התמחור.
- מגבלת קליטה: 10 לקוחות ב-7 ימים כברירת מחדל, עולה ל-200 אחרי Business
  Verification ו-Access Verification.
- דורש את אותו App Review, בגישה מתקדמת.

**סדר מומלץ:** קודם מספר אחד של הפלטפורמה (המדריך הציבורי, שלבים 1–14).
זה מוכיח שהמנגנון עובד, מאפשר לאשר את התבניות הראשונות, וזה מה שנדרש
ל-App Review ממילא. Embedded Signup נבנה אחר כך על אותה תשתית שליחה.
